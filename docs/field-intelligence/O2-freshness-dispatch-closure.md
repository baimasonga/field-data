# O2: dispatch and field closure for re-verification tasks

Operations first slice for the knowledge pillar's freshness tasks (K1). K1 generates
a supervisor queue of `queued` tasks and states that dispatch to collectors and proof
of field closure are later work. This slice is that work, and only that work. It does
not add sampling, routes, capacity planning, workload balancing, push delivery or
inclusion in the signed offline bundle; those remain pending (see Not in this slice).

## Contract

A task moves through explicit states. Every transition is version-checked and
recorded in an append-only event history; a task row is never rewritten silently.

    queued ──dispatch──> dispatched ──close──> closed
       │                    │  ▲  └─cancel──> cancelled
       │                    └──┘ (re-dispatch / reassign)
       ├────cancel────────────────────────> cancelled
       └─replaced observation (K1 worker)─> superseded

- `queued`: generated by K1 age policy. Unchanged.
- `dispatched`: assigned to one App User of the project, with an optional
  `visitBy` deadline. Re-dispatching a dispatched task reassigns it and keeps the
  earlier assignment in the event history. Closure evidence must be received after
  the dispatch time. Assigning a *different* App User restarts that clock; changing
  only the deadline for the same App User keeps it, so work already received is
  not invalidated.
- `closed`: a supervisor linked **fresh field evidence** (below). The closing
  observation is a normal K1 observation; the older observation and its history
  are untouched.
- `cancelled`: no visit evidence was obtained. A reason code
  (`access-blocked`, `safety`, `asset-removed`, `duplicate`, `other`) and a note are
  required. A cancellation never claims the asset was checked, and it carries no
  collector-performance meaning. Inaccessible or unsafe sites are an expected outcome.
- `superseded`: K1 worker behaviour for `queued` tasks only. A `dispatched` task is
  never superseded automatically, so the closing observation cannot race the worker
  into hiding the dispatch. A supervisor closes or cancels it.

`overdue` is derived (`dispatched` and `visitBy` passed). It is not a state and
triggers nothing.

### What counts as fresh field evidence

Closing links one existing asset observation. The server accepts it only when all hold,
checked inside the same transaction that locks the task:

1. The task is `dispatched` and the `If-Match` revision matches.
2. The observation belongs to the same asset and predicate, is newer in sequence than
   the observation the task was raised for, and has state `known` or `not-applicable`.
   `unknown` and `not-observed` are not evidence of a visit; cancel instead.
3. Its source claim version is on the asset's owning form, its submission is not
   deleted, and its stored integrity hash matches the stored XML.
4. Its provenance origin is `collected`. Imported, migrated and API-created
   submissions cannot close a field visit.
5. It was submitted by the assigned App User and received by the server after the
   latest dispatch time.
6. One observation closes at most one task.

Rejections name the failing condition. Basis and limits, stated plainly: "received
after dispatch" uses server receipt time, not device capture time. A collector who
captured offline before dispatch and synced afterwards passes this check, and device
clocks are not trusted for it. The supervisor sees the capture time and submitter and
remains the person who judges the visit. This is workflow evidence, not
proof of presence; proof-of-presence belongs to the evidence/trust area.

### Visibility

The App User inbox exposes only: asset name, external ID and type, predicate,
`visitBy`, form, and dispatch time. It never exposes the prior value, observation
history, review state or other collectors' tasks. This keeps the visit independent
of the earlier answer. A task is actionable only while the form is open and the App
User still holds `submission.create` on it. Reads and writes for supervisors require
`project.read`/`project.update` and `submission.read` on the asset's form, and
return 404 for tasks they cannot see.

## Data

Additive migration `20261009-05-add-reverification-dispatch.js`:
- `field_data_reverification_tasks`: status widened to the five states; new
  `revision`, `assigneeId`, `dispatchedAt`, `visitBy`, `closedAt`,
  `closureObservationId` (unique where not null); CHECK constraints tie each
  status to the columns it needs.
- `field_data_reverification_task_events`: append-only (trigger rejects update
  and delete). One row per dispatch, reassign, close and cancel, with actor,
  assignee, reason code, note, observation, request ID and request hash.
Rollback drops the new objects only when no task has left `queued`/`superseded`;
otherwise it refuses, because narrowing would lose the visit history.

## API

Under `/v1/field-data/projects/:projectId/reverification-tasks`:
- `GET` list (50 rows, opaque cursor), optional `status` filter; each row carries
  asset name and external ID, assignee display name, `overdue` and `revision`.
- `GET /:taskId` task, event history, and up to 20 candidate submissions by the
  assignee since dispatch on the asset's form (for the supervisor to cite).
- `POST /:taskId/dispatch` `{requestId, assigneeId, visitBy?, note}`.
- `POST /:taskId/close` `{requestId, observationId, note}`.
- `POST /:taskId/cancel` `{requestId, reasonCode, note}`.
All writes need `If-Match: "task-N"` (428 missing, 412 stale), a UUID `requestId`
(identical retries replay; a different payload under the same ID is rejected), and
are audited. All responses are `private, no-store`.

`GET /v1/field-data/app-user/reverification` lists the calling App User's own
dispatched tasks (inbox fields above only).

## Project queue

Supervisors need to see what is overdue across a project, not open assets one at a time.
`GET .../reverification-tasks` therefore also takes `overdue=true` (dispatched with a
`visitBy` that has passed; `overdue=false` means no filter) and `assigneeId`, alongside
`status`. Bad values are refused with 400, not ignored. A new
`GET .../reverification-tasks/summary` returns counts by status plus the overdue count and
the number of open (dispatched) tasks and overdue tasks held by each collector.

- **Access:** the forms the caller may read are resolved first and applied in the query, so
  pages are full and the counts and workload describe only work on forms the caller may
  read. A caller who can open the project but read none of its forms sees empty results;
  one with no project access gets 404.
- **Workload is a current count, not a score.** It is a number of open tasks to help spread
  the work. It ranks no one and measures no one's performance, because a task stays open
  for reasons the collector does not control (a blocked road, an unsafe site).
- **Screen:** a "Re-verification queue" section on the review screen shows the counts, the
  workload, filters (status, collector, overdue only), paging and an "Open asset" action
  that selects the task's form and opens its asset in the existing panel, where the task is
  dispatched, closed or cancelled. Only the newest request's answer is ever shown, and an
  answer in an unexpected shape becomes a retryable error.

## Acceptance

Actual PostgreSQL: dispatch/reassign/cancel/close happy paths and every closure
rejection; stale and missing revision; request replay and payload mismatch;
concurrent dispatch and close on one task; one-observation-one-task; viewer and
other-project isolation; assignee must be an App User of the project with
submission.create on the form; permission revoked after dispatch; K1 worker never
supersedes a dispatched task and still generates later tasks; event history is
append-only; migration rollback/reapply; App User sees only their own tasks and no
prior values. Browser: supervisor dispatch/close/cancel with stale-write recovery;
inbox listing; mobile layout.

## Not in this slice

Collector push notification for tasks, inclusion in the signed offline snapshot,
route/capacity planning and workload balancing, sampling and backcheck allocation,
accessibility history, and real-device pilot. None are claimed.

## Rollout

Deploy the migration before the API and client. Nothing is dispatched automatically
and no external message is sent. Existing `queued` tasks are unaffected. Roll back
API/client code with the data intact; the K1 queue keeps working.
