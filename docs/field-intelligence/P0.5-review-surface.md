# P0.5 — Give reviewers a queue, evidence, and audited override

## Decision this improves

A reviewer must be able to answer: **what needs attention, which exact claim version am I deciding on, what evidence and machine findings informed me, and who overrode what?**

P0.5 defines a claim-version review queue and an append-only decision history. Machine findings remain questions, not verdicts. A human may override a recommendation, but the reason and evidence snapshot are permanently attributable.

## What exists today

| Existing object or surface | Useful behavior | Gap for a review queue |
| --- | --- | --- |
| `submissions.reviewState` | Logical-submission states include `hasIssues`, `edited`, `approved`, and `rejected`; null is treated as received | State is submission-wide, not tied to one immutable claim version or evidence snapshot |
| Submission review PATCH | Authorized users can change review state and provide `X-Action-Notes` | No optimistic concurrency or structured override reason |
| `audits` | Records review changes and notes | Does not itself model a review case and immutable decision chain |
| `actees` | Existing form/project `acteeId` values provide stable targets for audit events | A submission has no actee, so claim identifiers belong in structured audit details rather than a new core relationship |
| `field_data_integrity_flags` | Stores explainable findings, evidence JSON, status, human decision, and note | Findings are form/instance-linked and each rule is reviewed independently; they are not a claim-level disposition |
| Submission verification UI | Shows evidence coverage and integrity findings without a score | It is a form/submission detail surface, not a cross-form work queue |
| P0.1 provenance | Explains origin, receipt, integrity hash, transform policy, and degradation | Needs to be assembled with claim and evidence context |
| P0.2 claim versions | Supplies stable claim and version identity | Needs review lifecycle and concurrency control |
| P0.3 evidence records | Supplies immutable source evidence and derivations | Needs a decision-time snapshot so later evidence additions do not rewrite history |

## Design decision: mutable case projection, immutable decisions

Use two additive sidecar tables:

- `field_data_review_cases` is the current work item and concurrency boundary for one claim version. Assignment, priority, and status may change under optimistic locking.
- `field_data_review_decisions` is an append-only decision chain. Each decision records the evidence and integrity-finding snapshot considered at that moment.

The queue is a projection over review cases joined to P0.1–P0.3 and existing integrity flags. The API must not persist a machine-generated truth score. Reasons are concrete and inspectable: missing evidence, provenance degradation, unresolved integrity finding, superseded version, or explicit manual referral.

Phase 0 does **not** automatically write `submissions.reviewState`. That field retains its existing Central meaning and UI behavior. The claim review result is version-specific and returned separately. A later reconciliation contract may map an accepted current claim to core review state, but implicit bidirectional synchronization would be unsafe.

## Schema

```sql
CREATE TABLE field_data_review_cases (
  id uuid PRIMARY KEY,
  "claimVersionId" uuid NOT NULL
    REFERENCES field_data_claim_versions(id) ON DELETE CASCADE,
  status text NOT NULL
    CHECK (status IN ('open', 'in-review', 'resolved', 'superseded')),
  priority text NOT NULL DEFAULT 'normal'
    CHECK (priority IN ('low', 'normal', 'high', 'urgent')),
  "reasonCodes" jsonb NOT NULL DEFAULT '[]'::jsonb,
  "assignedTo" integer NULL REFERENCES actors(id) ON DELETE SET NULL,
  revision integer NOT NULL DEFAULT 1 CHECK (revision > 0),
  "openedAt" timestamptz NOT NULL DEFAULT now(),
  "updatedAt" timestamptz NOT NULL DEFAULT now(),
  "resolvedAt" timestamptz NULL,
  "supersededByCaseId" uuid NULL
    REFERENCES field_data_review_cases(id) ON DELETE RESTRICT,
  "policyVersion" text NOT NULL DEFAULT 'p0.5',
  CHECK (
    (status = 'resolved' AND "resolvedAt" IS NOT NULL)
    OR
    (status <> 'resolved' AND "resolvedAt" IS NULL)
  )
);

CREATE UNIQUE INDEX field_data_review_cases_active_claim_version
  ON field_data_review_cases ("claimVersionId")
  WHERE status IN ('open', 'in-review', 'resolved');

CREATE TABLE field_data_review_decisions (
  id uuid PRIMARY KEY,
  "caseId" uuid NOT NULL
    REFERENCES field_data_review_cases(id) ON DELETE RESTRICT,
  "claimVersionId" uuid NOT NULL
    REFERENCES field_data_claim_versions(id) ON DELETE RESTRICT,
  "previousDecisionId" uuid NULL
    REFERENCES field_data_review_decisions(id) ON DELETE RESTRICT,
  sequence integer NOT NULL CHECK (sequence > 0),
  outcome text NOT NULL CHECK (outcome IN (
    'accepted',
    'needs-evidence',
    'returned-for-correction',
    'rejected'
  )),
  override boolean NOT NULL DEFAULT false,
  "reasonCode" text NOT NULL,
  note text NULL,
  "evidenceSnapshot" jsonb NOT NULL,
  "evidenceSnapshotHash" text NOT NULL,
  "integritySnapshot" jsonb NOT NULL,
  "reviewerId" integer NULL REFERENCES actors(id) ON DELETE SET NULL,
  "policyVersion" text NOT NULL DEFAULT 'p0.5',
  "createdAt" timestamptz NOT NULL DEFAULT now(),
  UNIQUE ("caseId", sequence),
  UNIQUE ("previousDecisionId"),
  CHECK (override = false OR note IS NOT NULL)
);
```

Application and database constraints must ensure a decision's `claimVersionId` matches its case, and its predecessor belongs to the same case with the preceding sequence. `reasonCodes` and snapshots must be JSON arrays of bounded, validated objects—not arbitrary unbounded payloads.

### Case lifecycle

1. A new claim version gets a case only when a deterministic routing reason or a manual referral exists. Absence from the queue is **not** approval.
2. Claim versions with degraded provenance, missing/mismatched required evidence, or unresolved integrity findings are opened automatically with explicit reason codes.
3. Taking a case moves `open` to `in-review`, sets `assignedTo`, and increments `revision`.
4. A terminal `accepted` or `rejected` decision resolves the case. `needs-evidence` and `returned-for-correction` keep the case open unless policy explicitly closes it.
5. When a new claim version supersedes the reviewed version, the old open case becomes `superseded` and a new case is evaluated from fresh evidence. Historical decisions remain unchanged.
6. Reopening creates a new decision in the same case only while the claim version remains current. It never mutates or deletes the earlier decision.

### Recommendation and override

The service may return a deterministic recommendation from transparent rules, for example `hold` because required evidence is missing. It must return the contributing rule IDs and versions. It must not return a composite truth/confidence score in Phase 0.

`override = true` means the human outcome differs from the current deterministic recommendation or reverses a prior human decision. Overrides require an allow-listed `reasonCode` and non-blank note. Every decision also appends a core `audits` event targeted at the owning form's existing actee; its details include `submissionId`, `submissionDefId`, `claimId`, `claimVersionId`, `caseId`, `decisionId`, outcome, override flag, and reason code. P0.5 does not create a submission actee. Audit failure fails the decision transaction.

## Backfill

Backfill does not reinterpret historic `submissions.reviewState` as a claim-version decision. Those states did not capture the evidence snapshot or claim version needed by P0.5.

Instead:

1. Evaluate only the current P0.2 claim version for each logical submission at rollout.
2. Open cases for deterministic current reasons: degraded/missing P0.1 provenance, required P0.3 evidence missing or mismatched, unresolved current integrity flags, or `submissions.reviewState = 'hasIssues'`.
3. When the only reason is an existing core review state, use reason `legacy-review-state` and include the state as asserted context, not a migrated decision.
4. Do not create synthetic reviewer identities, notes, decisions, or evidence snapshots.
5. Record `policyVersion = 'p0.5'` and rollout time in migration metrics.

The backfill is restart-safe and reports counts by reason. It must stop if the current `submission_defs` row cannot be mapped uniquely to a P0.2 claim version.

## API contract for the review UI

All endpoints are under `/v1/field-data` and return JSON. Authorization is evaluated through the underlying Central project and form. Users need existing submission-list/read permission to view cases and submission-update permission to assign or decide them.

### List the queue

`GET /v1/field-data/review-queue?projectId=12&xmlFormId=household&status=open&priority=high&assignedTo=me&reasonCode=evidence-missing&cursor=:cursor&limit=50`

Required response shape:

```json
{
  "items": [
    {
      "id": "a30e0374-b23d-4a02-a52c-4167c80a5eb2",
      "revision": 4,
      "status": "open",
      "priority": "high",
      "reasonCodes": ["evidence-missing", "integrity-unresolved"],
      "assignedTo": null,
      "openedAt": "2026-09-23T11:00:00Z",
      "claim": {
        "id": "b6e1d75d-4ef5-4e76-b37a-a868768e36db",
        "versionId": "4488be99-8e3b-4997-b24f-2dd365914f58",
        "ordinal": 2,
        "current": true,
        "rootInstanceId": "uuid:root"
      },
      "project": { "id": 12, "name": "District survey" },
      "form": { "xmlFormId": "household", "name": "Household" },
      "provenance": {
        "origin": "collected",
        "policyVersion": "p0.1",
        "degraded": null
      },
      "evidenceSummary": {
        "total": 3,
        "verified": 2,
        "missing": 1,
        "mismatch": 0
      },
      "integritySummary": {
        "total": 2,
        "unresolved": 1
      },
      "recommendation": {
        "outcome": "needs-evidence",
        "rules": [{ "id": "required-photo", "version": "1" }]
      },
      "latestDecision": null,
      "etag": "\"review-case-4\""
    }
  ],
  "nextCursor": "opaque-or-null"
}
```

The opaque cursor orders by priority rank, `openedAt`, and case ID. The default limit is `50`, maximum `100`. Filters are conjunctive. The API must avoid N+1 queries and return stable ordering while records are added.

### Get case detail

`GET /v1/field-data/review-queue/:caseId`

Returns the queue item plus:

- claim-version lineage summary;
- full P0.1 provenance envelope;
- cursor-paginated P0.3 evidence metadata and authorized content links;
- current integrity findings with rule version, explainable evidence, and prior finding decisions;
- immutable claim-review decision history;
- existing core `reviewState`, clearly labeled `submissionReviewState` and not merged with the claim result;
- relevant audit activity.

The response includes `ETag: "review-case-<revision>"`.

### Assign or release a case

`PATCH /v1/field-data/review-queue/:caseId`

Headers:

```http
If-Match: "review-case-4"
Idempotency-Key: 8cb984bd-0f8f-4b5a-aacd-c77444497973
```

Body:

```json
{ "assignedTo": 81, "status": "in-review" }
```

The update increments `revision`. Releasing uses `assignedTo: null` and normally returns status to `open`. It follows P0.4 replay semantics.

### Record a decision or audited override

`POST /v1/field-data/review-queue/:caseId/decisions`

Headers:

```http
If-Match: "review-case-4"
Idempotency-Key: de70bb7a-d116-41f5-b944-e9f30bf5d7ed
```

Body:

```json
{
  "outcome": "accepted",
  "override": true,
  "reasonCode": "verified-by-supervisor",
  "note": "The original photograph was inspected with the district lead.",
  "evidenceIds": ["15eb6037-1fd6-44af-a8b8-d71fbf29b631"],
  "integrityFindingIds": [92]
}
```

Within one transaction, the server:

1. locks the case and verifies `If-Match`;
2. confirms the claim version is still the intended version;
3. authorizes and resolves every referenced evidence/finding;
4. canonicalizes and hashes their decision-time snapshots;
5. appends the decision and core audit event;
6. updates case status/revision; and
7. commits the P0.4 idempotency result.

Response is `201` for a new decision or the replayed semantic result, with the new decision, case status, revision, ETag, and `Idempotency-Status`.

## Error cases

| Condition | HTTP | Stable code | Required behavior |
| --- | --- | --- | --- |
| Case is outside caller's project access | `404` | `REVIEW_CASE_NOT_FOUND` | Do not disclose existence |
| Missing or stale `If-Match` | `428` / `412` | `REVIEW_PRECONDITION_REQUIRED` / `REVIEW_REVISION_STALE` | Return current ETag only if caller can still read case |
| Claim version was superseded during review | `409` | `REVIEW_CLAIM_SUPERSEDED` | Return link to the new case when authorized |
| Override has no allow-listed reason or non-blank note | `422` | `REVIEW_OVERRIDE_REASON_REQUIRED` | Do not append a decision |
| Evidence is missing, unauthorized, or belongs to another scope | `422` or `404` | `REVIEW_EVIDENCE_INVALID` | Do not create a partial snapshot |
| Referenced finding changed after read | `412` | `REVIEW_CONTEXT_STALE` | Require reviewer refresh |
| Same idempotency key has a different request | `409` | `IDEMPOTENCY_KEY_REUSED` | Follow P0.4; append nothing |
| Decision audit append fails | `500` | `REVIEW_AUDIT_FAILED` | Roll back case and decision |
| User can read but not decide | `403` | Existing authorization code | Evidence remains read-only |
| Invalid queue cursor | `400` | `REVIEW_CURSOR_INVALID` | Never fall back to page one silently |

## Done when

P0.5 is complete only when:

- An authorized reviewer can list a stable, filtered, cursor-paginated queue across permitted projects/forms.
- A case detail view assembles the exact claim version, P0.1 provenance, P0.3 originals/derivations, current integrity findings, and decision history.
- Two reviewers cannot silently overwrite one another; stale decisions fail through ETag/revision checks.
- Every decision and override is append-only, attributable, idempotent, and paired atomically with a core audit event.
- Overrides require structured reason plus human note and retain the exact decision-time evidence/finding snapshot.
- A new claim version supersedes stale open work without changing historical decisions.
- Core `submissions.reviewState` remains behaviorally unchanged and visibly distinct.
- Integration and browser tests cover queue filters, authorization, evidence access, assignment races, stale context, override, replay, audit failure, and version supersession.
- Metrics expose queue age, reason mix, assignment latency, resolution time, overrides, stale-write conflicts, and superseded cases without ranking staff.

A queue table, a mock screen, or a review button without these end-to-end guarantees is not done.

## Open questions

1. Which deterministic reasons open a case in the first rollout, and which evidence types are required per form?
2. Should a terminal claim decision ever update core `submissions.reviewState`, and what explicit reconciliation action would make that safe?
3. May reviewers decide unassigned cases, or must assignment be mandatory for accountability?
4. Which roles may override recommendations or prior human decisions?
5. How long may a case remain `in-review` before assignment is released, and how is offline reviewer work protected?
6. Should existing integrity-finding decisions be frozen into claim snapshots by full value or by digest plus identifier?
7. What queue-level service objectives are useful without turning operational metrics into worker surveillance?
