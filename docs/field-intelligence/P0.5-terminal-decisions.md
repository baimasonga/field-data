# P0.5 terminal claim decisions

The Verification queue offers **Accepted** and **Rejected** for a case assigned
to the signed-in reviewer. Both require a nonblank note and one of that case's
routing reason codes. A reviewer must open the evidence panel before the
controls appear. The API checks form-level `submission.update` permission,
the case revision, assignment ownership, and the current claim version.
Overrides are not enabled in this slice.

Acceptance requires at least one linked original, all linked content hashes
verified, no contradictory evidence link, no unresolved integrity finding,
and no degraded claim or submission provenance. A blocked acceptance leaves
the case and decision history unchanged. Rejection remains a human judgment
with a recorded reason, note, and exact evidence/finding snapshot.

Both outcomes append an immutable decision and core audit entry, set the case
to `resolved` with `resolvedAt`, and increment its revision in one transaction.
Retries return the original decision via the P0.5 idempotency ledger. The
decision belongs to the exact P0.2 claim version. Neither outcome rewrites the
legacy ODK submission `reviewState`; operators can inspect both values.

Rollout follows the normal migration and deployment gate. The PostgreSQL
integration tests cover accepted and rejected cases, a blocked acceptance,
replay, snapshots, and the preserved legacy review state. If rollout fails,
revert the application deployment while retaining appended decisions and the
existing additive schema; never delete decision history to roll back the UI.
