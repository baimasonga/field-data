# App User fieldwork inbox and browser notifications

Open `/fieldwork` on this deployment. It does not require a Central Web User
login. A project supervisor opens the App User QR panel and uses **Copy private
access URL** to provide that App User's Collect server URL privately. The App
User enters that URL or key into the inbox. This grants the same access as the
Collect QR code. The inbox sends the key only in the Authorization header, keeps
it in tab memory, and never places it in a page URL, cookie, browser storage,
service-worker cache, or notification. Closing the tab clears the key; return
visits require entering it again.

The inbox shows only that App User's instructions, selected response form, due
date, status, and acknowledgment. Original answers, case identifiers, review
findings and other collectors' requests are excluded. Current submit access to
the selected form is required on every read and acknowledgment. Obsolete claims,
resolved cases and closed forms are marked unavailable for collection. Refresh
and bounded cursor pagination retrieve current server state. Acknowledgment is
idempotent and does not change the case revision, decision, or request status.
Reviewers use **Refresh back-checks** to see its timestamp in the existing list.

Continue downloading and submitting forms with ODK Collect, including its offline
workflow. This companion page does not alter Collect or cache task content offline.
Link the synced response through the existing reviewer workflow.

## Enabling browser push

The inbox works with push disabled. Set these variables securely on every backend
and worker process, then restart them:

- `FIELD_DATA_PUSH_ENABLED=true`
- `FIELD_DATA_PUSH_SUBJECT`: a real `mailto:` contact or HTTPS URL for the operator.
- `FIELD_DATA_PUSH_PUBLIC_KEY` and `FIELD_DATA_PUSH_PRIVATE_KEY`: one matching P256
  VAPID pair generated using `web-push.generateVAPIDKeys()`. Store the private key
  in the deployment secret manager; do not commit it or put it in client settings.

Keep the VAPID pair stable. After rotating it, browsers must turn off notifications
and opt in again with the new pair. Invalid, absent or mismatched keys disable push. No production keys are supplied
by this change. The public configuration endpoint exposes only the public key.
The deployment must serve HTTPS and run Central's existing durable audit worker
(`run-server.js` already starts it). Browser notification permission and Web Push
support are required. Supported push endpoints are Google's FCM, Mozilla Autopush,
and Apple's Web Push service; arbitrary destinations are rejected. On iOS,
platform support may require installing the page as a home-screen web app.

After connecting, choose **Enable browser notifications**. No permission prompt
or subscription is created before this action. Denial leaves the inbox usable.
Each App User can register up to three browser subscriptions. Subscription updates
are idempotent; another App User cannot take over or delete a registration.
**Turn off browser notifications** unsubscribes the browser and removes its server
registration. **Disconnect** also attempts this cleanup and clears the access key.
If cleanup fails, use browser site settings to disable notifications. Closing the
tab clears the key but retains opted-in push until it is explicitly disabled.

## Delivery and privacy

Request, cancellation and linking audits are enqueued in the same transaction as
the transition. Replays do not create another audit. The existing worker retries
transient failures up to five times with its ten-minute retry delay. It re-checks
collector access, deletion, current claim and transition status before sending.
An already-acknowledged, cancelled or obsolete request is not announced as new.
Expired subscriptions (404/410) are removed. Failures use a generic error without
logging provider bodies, endpoint capabilities, keys or assignment instructions.

Only a generic **Fieldwork inbox updated** notification and opaque request tag
are pushed. Its click opens the fixed `/fieldwork` page; no answers, question text,
credentials or provider-controlled URL appear on the lock screen. The worker
caches nothing. Push is best-effort, with at-least-once delivery; repeated attempts
share a notification tag. A provider's acceptance does not prove the App User saw
the notification. Acknowledgment in the inbox records that separate fact.

With push disabled or no subscription, audits are processed without sending and
tasks remain in the inbox. Enabling push later does not replay old announcements;
refresh the inbox for existing tasks. Delivery is independent of case decisions.
The device pilot and actual production browser delivery remain operator validation.

## API and rollback

App User bearer authentication is required; Web Users and public links are rejected.

- `GET /v1/field-data/app-user/backchecks?cursor=…`: own requests, up to 50 per page.
- `POST /v1/field-data/app-user/backchecks/:id/seen`: own acknowledgment.
- `GET /v1/field-data/app-user/push`: enabled state, public key, own registration IDs
  and endpoint hashes; never private keys, endpoints or authentication secrets.
- `POST /v1/field-data/app-user/push`: browser `PushSubscription.toJSON()` payload.
- `DELETE /v1/field-data/app-user/push/:id`: own registration removal.

Responses are private and no-store. Migration `20261009-02-add-app-user-backcheck-push`
adds an acknowledgment timestamp and subscriptions. Rollback/reapply retains both.
Disable push and drain queued audit jobs before rolling the application back to a
version without their worker handlers. Never drop fieldwork request history.

Validation uses generated test keys and mocked provider delivery; it sends no live
notifications. API tests exercise access boundaries, pagination precision, expiry,
worker failure/retry, stale cancellation and revoked access. Browser tests exercise
anonymous entry, safe text, acknowledgment, consent, opt-out, refresh retry,
credential cleanup and 320px layout.
