# P0.4 — Make every field action idempotent

## Decision this improves

Field devices and field offices operate across weak, intermittent networks. A caller must be able to retry a timed-out submission, evidence link, review decision, or action without creating duplicates—and the server must detect when the same retry key is reused for different work.

P0.4 defines one server-side replay contract while preserving ODK/OpenRosa behavior for clients that do not send a new header.

## What exists today

| Existing behavior | Protection it provides | Remaining gap |
| --- | --- | --- |
| Unique form/root instance ID in `submissions` and version-instance checks across `submission_defs` | Prevents many duplicate ODK submissions | Does not provide a common replay result or request-payload conflict check |
| `submission_attachments` primary key on `(submissionDefId, name)` | Prevents duplicate attachment rows | Same name with different bytes is not a general idempotency contract |
| Unique P0.1 provenance per `submissionDefId` | Prevents duplicate provenance envelopes | Covers only provenance |
| Unique integrity finding rule/version/pair | Deduplicates the same deterministic check | Does not cover reviewer decisions or field actions |
| `audits` append on actions | Preserves activity history | A retried request can append a second audit event if the action path is not idempotent |

Central already treats the ODK root instance ID as a natural retry key. P0.4 keeps that behavior; installing this feature must not require an upgraded Collect client.

## Design decision: scoped idempotency ledger

Create an additive ledger that reserves a key, binds it to a canonical request hash, and stores the committed resource/result reference.

The delivery model is **at least once at the transport boundary, exactly once per idempotency scope in the database**. The mutation and the ledger's successful result commit in the same transaction. A network response may still be lost; the next identical request replays the committed result.

Scope is `(projectId, operationType, idempotencyKey)`. This prevents collisions across projects and operation families while making reuse within one operation deterministic.

## Schema

```sql
CREATE TABLE field_data_idempotency_records (
  id uuid PRIMARY KEY,
  "projectId" integer NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  "operationType" text NOT NULL CHECK ("operationType" IN (
    'submission.create',
    'submission.version.create',
    'evidence.link.create',
    'review.decision.create',
    'field-action.create'
  )),
  "idempotencyKey" text NOT NULL,
  "requestHash" text NOT NULL,
  "hashAlgorithm" text NOT NULL DEFAULT 'sha256'
    CHECK ("hashAlgorithm" = 'sha256'),
  status text NOT NULL
    CHECK (status IN ('in-progress', 'succeeded', 'failed-retryable', 'failed-final')),
  "resourceType" text NULL,
  "resourceId" text NULL,
  "responseStatus" integer NULL,
  "responseJson" jsonb NULL,
  "errorCode" text NULL,
  "policyVersion" text NOT NULL DEFAULT 'p0.4',
  "createdAt" timestamptz NOT NULL DEFAULT now(),
  "updatedAt" timestamptz NOT NULL DEFAULT now(),
  "completedAt" timestamptz NULL,
  "expiresAt" timestamptz NULL,
  UNIQUE ("projectId", "operationType", "idempotencyKey"),
  CHECK (length("idempotencyKey") BETWEEN 1 AND 200),
  CHECK (
    (status = 'in-progress' AND "completedAt" IS NULL)
    OR
    (status <> 'in-progress' AND "completedAt" IS NOT NULL)
  )
);
```

`responseJson` stores only the minimal stable response needed for replay; it must not copy submission XML, evidence bytes, credentials, or signed download URLs. Sensitive or time-varying responses are rebuilt from `resourceType` and `resourceId` after authorization is rechecked.

### Key sources

| Operation | Key source | Compatibility rule |
| --- | --- | --- |
| New ODK submission | Server-derived from project, form, and root instance ID | No new client header required |
| ODK submission edit | Server-derived from project, form, logical submission, and version instance ID | Existing Central edit semantics remain authoritative |
| Attachment upload within submission multipart | Parent submission/version key plus normalized attachment name and content digest | Same name plus different bytes is a conflict |
| New Field Data API mutation | Required `Idempotency-Key` header | UUID recommended; opaque 1–200 printable ASCII characters |
| Offline field action batch | Stable client-generated action UUID for each item | Retrying a batch does not change item keys |

Keys must not contain PII or secrets because they appear in operational logs and uniqueness indexes.

### Canonical request hash

The hash is SHA-256 over a versioned canonical representation of mutation-relevant input:

```text
p0.4\n<operationType>\n<canonical-json-or-byte-digests>
```

Canonical JSON follows RFC 8785. Binary content contributes its media type, byte length, and SHA-256 digest, not an encoded copy. Transport-only fields, authorization tokens, trace IDs, and signed URL parameters are excluded. The canonicalization version is part of `policyVersion`; changing it requires a new policy version and compatibility tests.

### Transaction protocol

1. Start a database transaction.
2. Attempt to insert an `in-progress` ledger row.
3. If the scope already exists, lock it and follow the replay table below.
4. Perform the mutation and append its audit event in the same transaction.
5. Store the stable resource reference, response status, and safe response projection; mark `succeeded`.
6. Commit, then return the response.

Expected domain validation failures become `failed-final` and replay the same safe error. Infrastructure failures roll back the whole transaction, normally leaving no record. If an external side effect requires a committed reservation, mark `failed-retryable`; the same key may resume from the recorded checkpoint but a different request hash may not take over.

An `in-progress` row older than the configured lease is not deleted or blindly replaced. A recovery worker checks whether its resource committed, then completes or safely retries it.

## Backfill

There is no historical backfill. Past requests cannot be reconstructed with truthful keys or request hashes from resource rows and audits alone.

The migration records a rollout timestamp. P0.4 guarantees idempotency only for operations admitted after that boundary. Existing resources keep their current natural uniqueness constraints. Metrics and API documentation must make the boundary visible; the implementation must not synthesize ledger rows and imply certainty it does not have.

## API contract

### Request

New Field Data mutations send:

```http
Idempotency-Key: 9c621dab-635c-4cee-987d-17c1946dcb36
```

The key is required for P0.3 evidence-link creation, P0.5 review decisions, and future offline field actions. ODK endpoints continue accepting their existing protocol and use server-derived keys.

### Response headers

```http
Idempotency-Key: 9c621dab-635c-4cee-987d-17c1946dcb36
Idempotency-Status: created
```

`Idempotency-Status` is one of:

- `created` — this request committed the result.
- `replayed` — an earlier identical request committed the result.
- `in-progress` — work exists but is not yet safely replayable.

A replay returns the same semantic status and stable resource identity. It may receive a new `Date`, trace ID, ETag, or signed content URL.

### Replay decision table

| Existing ledger state | Request hash | Response |
| --- | --- | --- |
| None | Any valid hash | Reserve, execute, and return `created` |
| `succeeded` | Same | Reauthorize, return the committed result with `replayed` |
| `succeeded` | Different | `409 IDEMPOTENCY_KEY_REUSED` |
| `in-progress` within lease | Same | `409 IDEMPOTENCY_IN_PROGRESS` with `Retry-After` |
| `in-progress` | Different | `409 IDEMPOTENCY_KEY_REUSED` |
| `failed-final` | Same | Replay the recorded domain error |
| `failed-retryable` | Same | Resume from the recorded checkpoint or return `503` with `Retry-After` |
| Any state | Different authorization scope | `404` or `403` according to the underlying resource policy; never replay data |

## Error cases

| Condition | HTTP | Stable code | Required behavior |
| --- | --- | --- | --- |
| Missing key on required Field Data mutation | `400` | `IDEMPOTENCY_KEY_REQUIRED` | Do not begin mutation |
| Key is empty, too long, or non-printable | `400` | `IDEMPOTENCY_KEY_INVALID` | Do not persist malformed key |
| Existing key has different request hash | `409` | `IDEMPOTENCY_KEY_REUSED` | Return no prior response body or resource details |
| Identical work is still active | `409` | `IDEMPOTENCY_IN_PROGRESS` | Include bounded `Retry-After` |
| ODK instance ID already exists with identical content | Existing success/replay semantics | — | Return the existing resource without duplicate audit/evidence rows |
| ODK instance ID exists with different content | `409` | `INSTANCE_ID_CONFLICT` | Preserve the current Central conflict behavior and record metrics |
| Recovery cannot prove whether external effect happened | `503` | `IDEMPOTENCY_OUTCOME_UNKNOWN` | Quarantine for operator reconciliation; never execute blindly |
| Replay caller is no longer authorized | `404` or `403` | Existing authorization code | Authorization is evaluated again on every replay |

## Done when

P0.4 is complete only when:

- A response-lost retry of every covered operation returns one stable resource and creates one audit event.
- Reusing a key with a different payload deterministically returns `409` without disclosing the original resource.
- Stock ODK Collect submission and edit retries work without a new header.
- Mutation, audit event, P0.1 provenance, P0.2 claim mapping, and ledger result commit atomically where applicable.
- Recovery handles expired `in-progress` rows without blind duplicate side effects.
- Replays re-run authorization and never replay stale signed URLs or sensitive bodies.
- Load tests cover concurrent identical requests, concurrent conflicting requests, weak-network retry storms, and ledger-index performance.
- Metrics expose created, replayed, conflict, in-progress, expired-lease, and unknown-outcome counts by operation type.

The presence of an idempotency table or middleware alone is not completion.

## Open questions

1. What is the minimum retention period for keys, and may a key ever be reused after expiry?
2. Which failure classes should be persisted as `failed-final` rather than rolled back?
3. How should anonymous public-link submissions be scoped when no authenticated actor exists?
4. Should large offline action batches expose one batch key in addition to stable per-item keys?
5. Which external side effects require an outbox before they can join this guarantee?
6. Must replay reproduce the original HTTP status exactly, or only the same semantic resource and outcome?
