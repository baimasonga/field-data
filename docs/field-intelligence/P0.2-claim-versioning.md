# P0.2 — Version every claim

## Decision this improves

A reviewer, export, or later intelligence service must be able to answer: **which exact version of a field claim was used, what came before it, and which version is current?**

Today Central preserves submission XML versions, but their lineage is implicit in internal rows and flags. P0.2 gives that lineage a stable, public identity without changing ODK submission semantics or adding columns to core Central tables.

## What exists today

| Existing object | Useful behavior | Gap for field intelligence |
| --- | --- | --- |
| `submissions` | One logical submission; unique root `instanceId`; owns `reviewState`, `createdAt`, and `updatedAt` | Internal integer identity is not a stable claim identifier exposed to downstream systems |
| `submission_defs` | Stores each XML version and its `formDefId`, version `instanceId`, `current`, and `root` flags | The predecessor and version ordinal are implicit |
| `forms` / `form_defs` | Preserve the logical form and exact published form definition | Consumers must join several internal tables to explain which schema governed a claim version |
| `audits` | `submission.update.version` records edits, including `submissionDefId` for newer events | Older events were not backfilled; audit history is not a complete lineage index |
| `actees` | Gives projects and forms durable audit targets through their existing `acteeId` values | Submissions do not have actees; claim identity must not be smuggled into the audit-target hierarchy |
| `field_data_submission_provenance` | P0.1 records origin, timing, integrity hash, transformation policy, and degradation for each `submissionDefId` | It does not assign a stable claim identity or predecessor chain |

The ODK/OpenRosa contract remains authoritative: the root instance ID identifies the logical submission, and edits create new `submission_defs` rows under the same `submissionId`.

## Design decision: sidecar claim and claim-version tables

Create a stable opaque claim ID for each logical `submissions` row and a separate immutable claim-version ID for each `submission_defs` row.

This two-level model is deliberate:

- A **claim** survives edits and is the durable identity used by review queues and downstream references.
- A **claim version** points to one exact stored XML version and one exact `form_defs` version.
- The core `submissions` and `submission_defs` tables remain unchanged and continue to control ODK behavior.
- P0.1 provenance remains keyed to `submissionDefId`; P0.2 joins to it rather than copying it.
- A linear predecessor chain is explicit. Phase 0 does not support branching or merging.

## Schema

All names are additive and use the `field_data_*` namespace.

```sql
CREATE TABLE field_data_claims (
  id uuid PRIMARY KEY,
  "submissionId" integer NOT NULL UNIQUE
    REFERENCES submissions(id) ON DELETE CASCADE,
  "schemaVersion" text NOT NULL DEFAULT 'p0.2',
  "createdAt" timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE field_data_claim_versions (
  id uuid PRIMARY KEY,
  "claimId" uuid NOT NULL
    REFERENCES field_data_claims(id) ON DELETE CASCADE,
  "submissionDefId" integer NOT NULL UNIQUE
    REFERENCES submission_defs(id) ON DELETE CASCADE,
  ordinal integer NOT NULL CHECK (ordinal > 0),
  "previousVersionId" uuid NULL
    REFERENCES field_data_claim_versions(id) ON DELETE RESTRICT,
  "lineageBasis" text NOT NULL
    CHECK ("lineageBasis" IN ('created', 'backfill-id-order')),
  degraded jsonb NULL,
  "schemaVersion" text NOT NULL DEFAULT 'p0.2',
  "createdAt" timestamptz NOT NULL DEFAULT now(),
  UNIQUE ("claimId", ordinal),
  UNIQUE ("previousVersionId")
);
```

The implementation must also enforce that `previousVersionId`, when present, belongs to the same `claimId` and has `ordinal = current.ordinal - 1`. A deferred constraint trigger is acceptable because a plain foreign key cannot express both conditions.

UUIDs are generated by the application so migrations do not introduce a database-extension dependency. `ordinal` is lineage order, not business time. `submissionDefId` remains the source of truth for XML, `formDefId`, submitter, device, and current/root state.

### Live write behavior

Claim rows are written in the same database transaction that commits a submission version:

1. On a new logical submission, create one `field_data_claims` row and ordinal `1` claim version.
2. On an edit, lock the claim row, read the highest ordinal, and create exactly one successor.
3. Reject a second successor for the same predecessor. Retrying the same committed operation must return the existing claim version through the P0.4 idempotency contract.
4. If the sidecar write fails, the transaction fails. A new live submission version must never be committed without its P0.2 mapping after rollout.

## Backfill

Backfill is deterministic but explicitly degraded:

1. Group `submission_defs` by `submissionId`.
2. Create one application-generated claim UUID per group.
3. Order versions by `submission_defs.id ASC` and assign ordinals starting at `1`.
4. Link each row to the preceding ordinal.
5. Set `lineageBasis = 'backfill-id-order'` and:

```json
{
  "reason": "historical-lineage-inferred",
  "assumption": "submission_defs.id order reflects committed version order",
  "auditCompleteness": "not-required"
}
```

The backfill must report and stop on impossible groups: multiple `root` rows, multiple `current` rows, a root row that is not first by ID, or a version whose `submissionId` is missing. It must not silently repair core data.

Backfill does **not** infer lineage from `audits`, because older `submission.update.version` events may lack `submissionDefId`. `createdAt` is retained as descriptive metadata but is not used for ordering because timestamps can tie.

## API contract

The claim API is additive and versioned.

### Get a claim and its versions

`GET /v1/projects/:projectId/forms/:xmlFormId/submissions/:instanceId/claim`

The route resolves the existing logical submission with normal Central authorization, then returns:

```json
{
  "id": "b6e1d75d-4ef5-4e76-b37a-a868768e36db",
  "submissionId": 731,
  "rootInstanceId": "uuid:root",
  "currentVersionId": "4488be99-8e3b-4997-b24f-2dd365914f58",
  "versions": [
    {
      "id": "4488be99-8e3b-4997-b24f-2dd365914f58",
      "ordinal": 2,
      "previousVersionId": "e6d10d22-f9cb-4970-a9c5-27afba3a09b7",
      "instanceId": "uuid:edit-2",
      "formVersion": "2026-09-01",
      "current": true,
      "root": false,
      "lineageBasis": "created",
      "degraded": null,
      "provenance": {
        "origin": "collected",
        "policyVersion": "p0.1"
      }
    }
  ]
}
```

`versions` is ordered by ascending ordinal. Internal `submissionDefId` may be included for administrators but is not the public identity. XML is not embedded; existing submission XML endpoints retain their authorization and content-negotiation rules.

### Get one claim version

`GET /v1/field-data/claim-versions/:claimVersionId`

Returns the same version representation plus project, form, claim, and provenance links. The server must authorize through the referenced submission's project and form; possession of a UUID is never sufficient.

## Error cases

| Condition | HTTP / migration behavior | Stable code | Required behavior |
| --- | --- | --- | --- |
| Submission does not exist or is not visible | `404` | `CLAIM_NOT_FOUND` | Do not disclose cross-project existence |
| Claim mapping is absent after rollout | `500` | `CLAIM_MAPPING_MISSING` | Log the `submissionId`; never synthesize an identity in the read path |
| Two successors race | `409` | `CLAIM_VERSION_CONFLICT` | Roll back and let the caller retry through idempotency |
| Predecessor belongs to another claim | `409` | `CLAIM_LINEAGE_INVALID` | Reject the transaction |
| Historical group violates root/current invariants | Backfill stops | `CLAIM_BACKFILL_AMBIGUOUS` | Emit the affected IDs; do not guess |
| Claim UUID is malformed | `400` | `CLAIM_VERSION_ID_INVALID` | No database query with a coerced value |

## Done when

P0.2 is complete only when all of the following are demonstrated:

- Every new or edited submission version atomically receives one stable claim-version identity.
- A claim's ordered chain can be retrieved with its exact form definition and P0.1 provenance.
- Concurrent edits cannot create two successors for one predecessor.
- Backfill is restart-safe, reports its assumptions, and fails on ambiguous historical groups.
- Project/form authorization is enforced for both lookup forms.
- Integration tests cover create, edit, retry, concurrent edit, purge/cascade behavior, authorization, and a multi-version backfill.
- Operational metrics report missing mappings and lineage conflicts.

A table existing, or a migration merely applying, is not sufficient.

## Open questions

1. Should a future correction workflow permit branches, or must all conflict resolution create a new linear successor?
2. On a Central purge, should claim identifiers disappear with the source record or leave a non-identifying tombstone for external references?
3. Should public APIs expose the internal numeric `submissionId`, or only the claim UUID and root instance ID?
4. Does a draft submission receive a claim immediately, or only when its first non-draft version is accepted?
5. Should the chain endpoint use cursor pagination once unusually long edit histories are observed?
