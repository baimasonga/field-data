# P0.3 — Treat evidence as a first-class record

## Decision this improves

A reviewer must be able to decide whether a specific claim version is supported by authentic source material, while preserving the original bytes and keeping machine-derived interpretations visibly separate.

P0.3 creates an immutable evidence registry and explicit claim-to-evidence links. It does not turn every media file into evidence, and it does not allow an AI output to replace an original.

## What exists today

| Existing object | Useful behavior | Gap for field intelligence |
| --- | --- | --- |
| `submission_defs` | Preserves exact XML for each submission version | XML is not represented as an addressable evidence record |
| `submission_attachments` | Links a named attachment to the exact `submissionDefId`; identifies client audit attachments | Rows are transport/storage metadata, not an immutable evidence contract |
| `blobs` | Stores attachment bytes and SHA-1/MD5 metadata, locally or through configured object storage | Legacy hashes and storage state do not express evidence integrity, retention, or derivation |
| `client_audits` | Parses device audit logs for inspection | Parsed rows are derived from an attachment; the relationship to the original is not a general evidence graph |
| `field_data_media` | Provides an administrative media library | Records are not claim-scoped and are deletable; this table must not be reused as the evidence store |
| `field_data_submission_provenance` | Captures P0.1 origin and integrity hash for a submission version | Provenance describes the claim envelope, not all supporting artifacts |
| `field_data_claim_versions` | P0.2 identifies the exact claim version | It needs immutable, typed evidence edges |

## Design decision: registry, links, and derivations

Use three additive sidecar tables:

1. `field_data_evidence_records` identifies an original source without copying or mutating its bytes.
2. `field_data_claim_evidence` links that source to an exact P0.2 claim version.
3. `field_data_evidence_derivations` stores machine-produced interpretations separately from originals.

Original bytes remain in their current authoritative stores: submission XML in `submission_defs.xml`, and attachments in `blobs` through `submission_attachments`. The evidence registry records a SHA-256 digest over those exact stored bytes. A derived thumbnail, transcript, OCR result, embedding, classification, or redaction is never written back into an original record.

Evidence records and links are append-only after creation. Corrections create a new record or link and explicitly supersede the old one; they do not update historical meaning in place.

## Schema

```sql
CREATE TABLE field_data_evidence_records (
  id uuid PRIMARY KEY,
  "sourceKind" text NOT NULL
    CHECK ("sourceKind" IN ('submission-xml', 'attachment', 'client-audit')),
  "submissionDefId" integer NOT NULL
    REFERENCES submission_defs(id) ON DELETE RESTRICT,
  "attachmentName" text NULL,
  "blobId" integer NULL REFERENCES blobs(id) ON DELETE RESTRICT,
  "contentHash" text NOT NULL,
  "hashAlgorithm" text NOT NULL DEFAULT 'sha256'
    CHECK ("hashAlgorithm" = 'sha256'),
  "mimeType" text NOT NULL,
  "byteSize" bigint NOT NULL CHECK ("byteSize" >= 0),
  "capturedAt" timestamptz NULL,
  "receivedAt" timestamptz NOT NULL,
  "integrityStatus" text NOT NULL
    CHECK ("integrityStatus" IN ('verified', 'unverified', 'missing', 'mismatch')),
  "retentionClass" text NOT NULL DEFAULT 'source-record',
  "policyVersion" text NOT NULL DEFAULT 'p0.3',
  degraded jsonb NULL,
  "createdAt" timestamptz NOT NULL DEFAULT now(),
  CHECK (
    ("sourceKind" = 'submission-xml' AND "attachmentName" IS NULL AND "blobId" IS NULL)
    OR
    ("sourceKind" IN ('attachment', 'client-audit') AND "attachmentName" IS NOT NULL)
  ),
  UNIQUE ("submissionDefId", "sourceKind", "attachmentName")
);

CREATE TABLE field_data_claim_evidence (
  id uuid PRIMARY KEY,
  "claimVersionId" uuid NOT NULL
    REFERENCES field_data_claim_versions(id) ON DELETE CASCADE,
  "evidenceId" uuid NOT NULL
    REFERENCES field_data_evidence_records(id) ON DELETE RESTRICT,
  relation text NOT NULL
    CHECK (relation IN ('supports', 'contradicts', 'context')),
  "supersedesLinkId" uuid NULL
    REFERENCES field_data_claim_evidence(id) ON DELETE RESTRICT,
  "createdBy" integer NULL REFERENCES actors(id) ON DELETE SET NULL,
  "createdAt" timestamptz NOT NULL DEFAULT now(),
  UNIQUE ("claimVersionId", "evidenceId", relation)
);

CREATE TABLE field_data_evidence_derivations (
  id uuid PRIMARY KEY,
  "evidenceId" uuid NOT NULL
    REFERENCES field_data_evidence_records(id) ON DELETE RESTRICT,
  kind text NOT NULL,
  algorithm text NOT NULL,
  "algorithmVersion" text NOT NULL,
  "outputJson" jsonb NULL,
  "storageKey" text NULL,
  "contentHash" text NOT NULL,
  "qualityJson" jsonb NULL,
  "supersedesDerivationId" uuid NULL
    REFERENCES field_data_evidence_derivations(id) ON DELETE RESTRICT,
  "createdAt" timestamptz NOT NULL DEFAULT now(),
  CHECK (("outputJson" IS NULL) <> ("storageKey" IS NULL))
);
```

`blobId` is nullable because an expected attachment can exist before bytes finish arriving, and historical bytes may be missing. Such records use `integrityStatus = 'missing'` and cannot be presented as verified evidence. Application validation must ensure that any non-null `blobId` and `attachmentName` belong to the same `submissionDefId` through `submission_attachments`.

The implementation must deny `UPDATE` and `DELETE` for evidence records, links, and derivations through application APIs. Database permissions or protection triggers should enforce append-only behavior for runtime roles while still allowing the existing purge workflow to perform an explicit, audited retention action.

### Integrity rules

- Hash the exact bytes at rest with SHA-256. For XML, define UTF-8 encoding of the stored `submission_defs.xml` text as the byte sequence.
- For encrypted submissions, the stored ciphertext is the original and is what gets hashed; decrypted material is a derivation with stricter access policy.
- `verified` means the recorded digest was recomputed from available bytes and matched. It does not mean the claim is true.
- Derived output includes its producer and version, is reproducible where possible, and always links back to the original evidence ID.
- The evidence API labels `missing`, `unverified`, and `mismatch` prominently; it never drops them from counts.

## Backfill

Backfill runs after P0.2:

1. Register each historical `submission_defs.xml` as `submission-xml` and link it to the matching claim version with `relation = 'context'`.
2. Register every `submission_attachments` row. Use `client-audit` when `isClientAudit` is true and `attachment` otherwise.
3. When bytes are available, stream them through SHA-256, record size and MIME type, and set `integrityStatus = 'verified'`.
4. When bytes are absent or object storage cannot produce them, set `missing` or `unverified` and record a structured `degraded` reason. Do not fabricate a hash.
5. Link an attachment only to the claim version represented by its `submissionDefId`; do not copy attachment links forward across edits.

Historical `capturedAt` is usually unknown. Backfill leaves it null and records:

```json
{
  "reason": "historical-capture-time-unknown",
  "hashTiming": "computed-during-p0.3-backfill"
}
```

The process is restart-safe through the source uniqueness constraint. It reports byte totals, missing blobs, hash mismatches, and records skipped because their P0.2 mapping is absent. Hashing must be batched and rate-limited so it does not starve submission traffic.

## API contract

### List evidence for one claim version

`GET /v1/field-data/claim-versions/:claimVersionId/evidence?cursor=:cursor&limit=50`

Response:

```json
{
  "items": [
    {
      "id": "15eb6037-1fd6-44af-a8b8-d71fbf29b631",
      "sourceKind": "attachment",
      "relation": "supports",
      "name": "plot-photo.jpg",
      "mimeType": "image/jpeg",
      "byteSize": 2841047,
      "contentHash": "sha256:8e4f...",
      "capturedAt": null,
      "receivedAt": "2026-09-23T10:10:00Z",
      "integrityStatus": "verified",
      "degraded": null,
      "downloadUrl": "/v1/field-data/evidence/15eb6037-1fd6-44af-a8b8-d71fbf29b631/content",
      "derivations": [
        {
          "id": "499e1478-97f9-43c0-9d87-cae370bf273b",
          "kind": "thumbnail",
          "algorithm": "sharp",
          "algorithmVersion": "0.34.4"
        }
      ]
    }
  ],
  "nextCursor": null
}
```

The cursor is opaque and stable over `(createdAt, id)`. `limit` is capped at `100`. Derived payloads are summarized; large content is fetched separately.

### Get evidence metadata or content

- `GET /v1/field-data/evidence/:evidenceId`
- `GET /v1/field-data/evidence/:evidenceId/content`
- `GET /v1/field-data/evidence/:evidenceId/derivations/:derivationId/content`

All routes authorize through the owning submission's project. Content responses reuse existing safe download behavior, MIME headers, and range support. A signed object-store URL may be returned, but it must be short-lived and scoped to the authorized object.

### Register an additional evidence link

`POST /v1/field-data/claim-versions/:claimVersionId/evidence-links`

```json
{
  "evidenceId": "15eb6037-1fd6-44af-a8b8-d71fbf29b631",
  "relation": "supports",
  "supersedesLinkId": null
}
```

This route requires the P0.4 idempotency contract. Phase 0 does not introduce arbitrary file upload; submission attachment upload remains the supported original-ingest path.

## Error cases

| Condition | HTTP / backfill behavior | Stable code | Required behavior |
| --- | --- | --- | --- |
| Evidence belongs to another project | `404` | `EVIDENCE_NOT_FOUND` | Do not reveal cross-project metadata |
| Referenced bytes are missing | `409` for content; metadata remains `200` | `EVIDENCE_BYTES_MISSING` | Preserve the record and degraded state |
| Recomputed hash differs | `409` for content | `EVIDENCE_HASH_MISMATCH` | Mark mismatch, alert, and never serve as verified |
| Evidence already linked identically | `200` replay through idempotency | — | Return the original link |
| Same idempotency key, different link request | `409` | `IDEMPOTENCY_KEY_REUSED` | Follow P0.4 |
| Link crosses unrelated submissions without permission | `422` | `EVIDENCE_SCOPE_INVALID` | Reject; cross-claim evidence is explicit future work |
| Attempt to update or delete an evidence record | `405` | `EVIDENCE_IMMUTABLE` | Require a superseding record or retention workflow |
| Derivation identifies no producer version | `422` | `DERIVATION_VERSION_REQUIRED` | Reject the derivation |

## Done when

P0.3 is complete only when:

- Every new claim version has an addressable XML evidence record and every received attachment has a typed evidence record.
- A reviewer can retrieve evidence metadata and authorized original content from a claim version.
- SHA-256 is verified against exact stored bytes, including streamed object-store content.
- Original evidence and derivations are presented and stored separately.
- Missing bytes and hash mismatches remain visible and cannot be mislabeled as verified.
- Append-only and retention behavior is enforced, not merely documented.
- Backfill is restart-safe, bounded, observable, and tested against missing blobs and encrypted submissions.
- Integration tests cover authorization, ranges/downloads, cross-project isolation, immutable writes, derivations, purge policy, and P0.4 retries.

Creating the tables without ingestion, retrieval, integrity verification, and reviewer-visible behavior is not done.
