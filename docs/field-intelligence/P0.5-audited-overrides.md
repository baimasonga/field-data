# Audited supervisor acceptance

The assigned reviewer may accept a current claim despite degraded provenance or
unresolved integrity findings when they also have `project.update` permission on
the owning project. Both permissions are checked on every request, including
replays. Case detail returns `overridePolicy.allowed` and the allowed reason codes;
the evidence panel shows an explicit **Accept with supervisor override** action.

The decision requires `override: true`, `outcome: accepted`, the allowlisted reason
`verified-by-supervisor`, and a nonblank note (maximum 4,000 characters) explaining
the verification. At least one provenance limitation or unresolved finding must
exist. Overrides cannot bypass missing, unverified, mismatched or contradictory
evidence, pending backchecks, assignment ownership, current-version checks, or
revision checks. Reopening and replacing terminal human decisions use the separate
[reconsideration policy](P0.5-decision-reconsideration.md).

The transaction appends an immutable decision with exact evidence and finding
snapshots and a core audit with the reviewer, reason, override flag, and the
provenance limitations and findings present at decision time. It resolves the
case and increments its revision atomically. Source provenance and findings keep
their limitations; the legacy submission review state is not rewritten.

Retries use the existing idempotency ledger. Override requests have distinct
canonical hashes; ordinary decision hashes remain compatible with deployed
requests. Existing workload metrics count the recorded override. No schema
migration is needed. Rollback reverts application code while retaining history.

API regressions cover permissions, validation, normal acceptance blocking,
tampered evidence, replay, stale writes, immutable history, audit context and
metrics. Browser fixtures cover explicit supervisor acceptance and history.
Actual offline capture and sync still require the scheduled ODK Collect pilot.
