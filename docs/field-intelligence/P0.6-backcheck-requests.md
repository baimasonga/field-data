# P0.6 back-check requests

## Reviewer workflow

An assigned reviewer requests one back-check for a current claim version. They
choose a published, open response form in the same project and a different
project App User who can submit to that form, specify what
must be verified, and optionally set a due date. The App User collects a new
submission of the selected form through ODK Collect. Collect's existing local storage
and retry path work offline; the reviewer links its instance ID only after it
syncs to the server. The case then shows links to both submissions and the
back-check's recorded provenance. A missing or degraded time remains visible.

The reviewer makes the final decision. Requesting, linking, or seeing a
back-check never automatically accepts a claim or finds misconduct. An
unlinked request blocks a terminal review decision.

## API and protection

- `GET /v1/field-data/review-queue/:caseId/backcheck-forms` lists readable,
  published, open forms in the same project with their eligible App Users.
- `GET /v1/field-data/review-queue/:caseId/backcheck-assignees` lists eligible
  App Users for the form to authorized reviewers.
- `POST /v1/field-data/review-queue/:caseId/backchecks` accepts `If-Match` with
  the case revision and `{requestId, assignedTo, question, dueAt, responseXmlFormId}`. `requestId`
  is a stable client UUID for retry. Reusing it with changed input is rejected.
- `GET /v1/field-data/review-queue/:caseId/backchecks` lists requests and the
  server's provenance for a linked submission, scoped by form read permission.
- `POST /v1/field-data/review-queue/:caseId/backchecks/:id/cancel` accepts
  `If-Match` and `{requestId, reason}`. The assigned reviewer can cancel a
  pending request with an audited reason, retaining its original assignment
  and allowing a replacement request to another eligible collector.
- `POST /v1/field-data/review-queue/:caseId/backchecks/:id/link` accepts
  `If-Match` and `{instanceId}`. Only the assigned reviewer can link a new,
  synced, current submission of the selected response form from the selected App User.
  Linking the same result again is safe; linking another result is rejected.

The server locks the review case for each transition, keeps one pending
request per case, writes an audit entry for each actual transition, and
increments the case revision. The table survives a migration rollback when it
contains fieldwork history. Source ODK submissions remain in Central; request
rows link to them and do not copy their answers or attachments.

## Pilot and remaining work

Pilot with a form assigned to two distinct App Users; track requests linked,
time to link, and requests still pending after their due date. Verify an
offline Collect submission syncs once and can be linked after receipt. Roll
back the new API and UI if assignment or provenance links misidentify a
collector; retain the audit and request rows. Cancellation and replacement are
implemented in [the cancellation follow-up](../feature-delivery/backcheck-cancellation.md).
[Pinned answer comparison](P0.6-backcheck-comparison.md) is implemented as reviewer
decision support. [Dedicated response forms](P0.6-dedicated-backcheck-forms.md) are implemented.
Push notification to the selected App User remains a separate follow-on package. Cancellation
does not withdraw a form already stored on an offline device.
